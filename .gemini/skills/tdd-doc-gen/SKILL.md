# Skill: tdd-doc-gen

## Описание

Навык автоматизированной генерации **исчерпывающих** Moduleных тестов и обновления документации кода.
Ключевые принципы: тест генерируется для КАЖДОЙ функции, КАЖДОГО параметра и КАЖДОГО граничного сценария.
Переходить к документированию разрешено ТОЛЬКО после успешного прохождения всех тестов.

---

## Протокол выполнения (Обязателен при каждом изменении `.py` файлов)

### Шаг 1 — Документирование директорий

При создании любой новой директории ОБЯЗАТЕЛЬНО создать в ней файл `README.md` на русском языке с описанием:
- Предназначение модуля.
- Принципы его работы.
- List файлов и их роли.

---

### Шаг 2 — Анализ влияния (Impact Analysis)

**Перед написанием теста** — провести полный анализ цепочки зависимостей изменённого кода.

#### Чек-лист анализа:
1. Прочитать изменённый файл полностью (импорты, классы, функции, их сигнатуры).
2. Найти все файлы, которые **импортируют** изменённый Module или функцию:
   ```powershell
   # Поиск всех импортов модуля в проекте
   grep -r "from src.module_name import" . --include="*.py"
   grep -r "import src.module_name" . --include="*.py"
   ```
3. Определить **транзитивные зависимости** — модули, которые используют зависимые модули.
4. Составить list всех блоков для тестирования:
   - Изменённый блок (прямое тестирование).
   - Все прямые зависимости (Regression Tests).
   - Потенциально затронутые интеграционные точки (end-to-end сценарии).

---

### Шаг 3 — Validation запуска (Smoke Test)

Перед генерацией тестов убедиться, что код работоспособен:
```powershell
# Запуск минимального smoke-теста на импорт модуля
python -c "from src.target_module import TargetClass; print('OK')"
```

Если импорт не проходит — сначала исправить код, затем переходить к генерации тестов.

---

### Шаг 4 — Генерация тестов (Scenario-based, обязательный)

#### 4.1 Структура тестового файла

Каждый тестовый файл `tests/test_<module_name>.py` **MUST** следовать этому шаблону:

```python
# -*- coding: utf-8 -*-
# =============================================================================
# Process Name: Тесты модуля src/<module_name>
# =============================================================================
# Description:
#   Исчерпывающее тестирование всех публичных функций и классов модуля.
#   Покрытие: прямые тесты, граничные условия, регрессионные сценарии.
#
# File: tests/test_<module_name>.py
# Project: ai-assistant
# Package: tests
# Author: hypo69
# Copyright: © 2026 hypo69
# =============================================================================
```

#### 4.2 Обязательное покрытие тестами

Для КАЖДОЙ публичной функции и метода **MUST** быть созданы тесты для:

| Категория             | Описание                                               |
|-----------------------|--------------------------------------------------------|
| **Happy Path**        | Нормальный ввод, ожидаемый результат                   |
| **Edge Cases**        | Пустые строки, `0`, `[]`, `{}`, пустые коллекции      |
| **Type Variants**     | Разные допустимые типы аргументов                      |
| **Boundary Values**   | Минимальные и максимальные допустимые значения         |
| **Error Scenarios**   | Invalid Input, несуществующие ресурсы                |
| **Regression**        | Тесты на зависимые блоки, выявленные в Шаге 2         |

#### 4.3 Правила максимального комментирования тестов (ОБЯЗАТЕЛЬНО)

**КАЖДАЯ** переменная в тестах **MUST** быть прокомментирована.
**КАЖДЫЙ** шаг выполнения **MUST** иметь пояснение.
**КАЖДОЕ** утверждение (assert) **MUST** объяснять, что именно проверяется и почему.

**Образец максимально подробного теста:**

```python
def test_process_user_data_happy_path(self):
    """Тестирование нормального сценария обработки данных пользователя.

    Check: correct dictionary с обязательными полями Returns True.
    Зависимости: function используется в UserManager.create_session().
    """
    # --- Подготовка входных данных (Arrange) ---

    # Тестовые данные: dictionary с обязательным полем 'user_id'.
    # Значение '42' — стандартный целочисленный идентификатор.
    test_data: dict = {'user_id': 42, 'name': 'Тест'}

    # --- Выполнение тестируемой функции (Act) ---

    # Вызов тестируемой функции с корректными входными данными.
    # Ожидается возврат True при успешной обработке.
    result: bool = process_user_data(test_data)

    # --- Check результата (Assert) ---

    # Check: function должна вернуть True для корректного словаря.
    # Нарушение: если вернёт False или exception — логика обработки сломана.
    assert result is True, (
        f"process_user_data() должна вернуть True для корректного ввода, "
        f"получено: {result!r}"
    )


def test_process_user_data_empty_dict(self):
    """Тестирование граничного случая: empty dictionary.

    Check: empty dictionary {} активирует ранний возврат (Early Return).
    Стандарт: по CODE_RULES.md §3.4, function обязана вернуть False.
    """
    # --- Подготовка входных данных (Arrange) ---

    # Граничное значение: empty dictionary — допустимый тип, но пустые данные.
    # Ожидается активация ветки раннего возврата (Early Return) в функции.
    empty_data: dict = {}

    # --- Выполнение (Act) ---

    # Вызов функции с пустым словарём.
    # Function должна обнаружить отсутствие данных и вернуть False без исключений.
    result: bool = process_user_data(empty_data)

    # --- Check (Assert) ---

    # Check: empty dictionary должен возвращать False (Early Return).
    # Нарушение: возврат True означает, что check входных данных не работает.
    assert result is False, (
        f"process_user_data() должна вернуть False для пустого словаря, "
        f"получено: {result!r}"
    )
```

### Шаг 5 — Запуск и верификация

```powershell
# Запуск только новых тестов
pytest tests/test_<module_name>.py -v

# Запуск полного регрессионного прогона по затронутым модулям
pytest tests/test_<module_name>.py tests/test_<dependent_module>.py -v

# Check покрытия для конкретного модуля
pytest tests/test_<module_name>.py --cov=src/<module_name> --cov-report=term-missing
```

**Правило:** Если хотя бы один тест падает — исправить код, не переходить к документированию.

---

### Шаг 6 — Документирование (только после зелёных тестов)

После прохождения всех тестов — обновить Docstrings в исходном файле:
- Формат: `hypo69 docblock` (секции: Args, Returns, Exceptions, Examples).
- Запрет: Sphinx/reST конструкции (`.. module::`, `:param:`, `:returns:`, `:raises:`).
- Язык: Python — русский/английский.

---

## Правила (жёсткие ограничения)

- ❌ НЕ переходить к документированию, если тесты НЕ проходят.
- ❌ НЕ создавать тест без комментария к каждой переменной и каждому шагу.
- ❌ НЕ оставлять тесты без регрессионного покрытия зависимых блоков.
- ✅ ВСЕГДА анализировать цепочку зависимостей перед написанием теста.
- ✅ ВСЕГДА добавлять сообщение к assert: `assert ..., "Что сломано и почему"`.
- ✅ ВСЕГДА следовать стандарту оформления из `CODE_RULES.md`.
