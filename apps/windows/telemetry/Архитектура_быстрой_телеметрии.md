# Архитектура быстрой телеметрии и мониторинга Windows

## 1. Обзор архитектуры

Архитектура подсистемы построена на четком разделении ответственности между двухуровневыми компонентами:
1. **Разовые доменные коллекторы аудита** (`apps.windows.core.modules`) — выполняют глубокий точечный срез состояния системы по требованию (через CLI или AI-агент).
2. **Непрерывный сервис телеметрии и агрегатор** (`apps.windows.telemetry`) — переводит данные в динамический поток замеров, обрабатывает события реального времени и сохраняет хронологию в кольцевую базу данных SQLite (`telemetry.db`).

## 2. Многоуровневые источники аппаратных данных (Hardware Sensor Tiering)

В отличие от упрощенных схем, подсистема сбора сенсоров `SensorCollector` задействует иерархическую систему провайдеров (`apps.windows.hardware.providers`):

* **Tier 1 (Native Windows API & psutil):**
  * Загрузка ЦП, физической памяти (RSS/Swap), базовые дисковые и сетевые счетчики.
  * Прямой опрос WMI (`Win32_Processor`, `Win32_PhysicalMemory`) и DXGI для видеокарт.
* **Tier 2 Primary (LibreHardwareMonitor REST API & WMI):**
  * **Основной источник температур и нагрузок:** `LhmService` опрашивает встроенный Web REST API (`http://localhost:8085/data.json`) или WMI-пространство `root\LibreHardwareMonitor`.
  * Предоставляет точные показания зон нагрева (VRM, чипсет, CPU Package, GPU Hotspot), напряжений, частот и оборотов кулеров (RPM).
* **Tier 3 / Specialized Providers (HWiNFO, AIDA64, CPU-Z, GPU-Z):**
  * Поддержка чтения Shared Memory (`AIDA64_SensorValues`, `Global\HWiNFO_SENS_SM2`), CLI-отчетов и NVML/nvidia-smi.
* **Сетевые провайдеры (`InternetSpeedSensor`):**
  * Замер качества интернет-канала (Ping до DNS 8.8.8.8, Download/Upload Mbps, время разрешения DNS).

## 3. Специализированные сенсоры реального времени

1. **Сенсор отлова "дребезга" устройств (`DeviceFlappingSensor`):**
   * Работает в фоновом потоке с интервалом **1,0 секунды**.
   * Задействует `SetupAPI` для фиксации мгновенных отключений/подключений периферии (USB, аудио, мониторы, графические планшеты) и отслеживания PnP-кодов ошибок (Code 10, 43, 28).
2. **Монитор файловых событий (`FileCollector` / `DirectoryWatcher`):**
   * Перехватывает события создания, изменения и удаления файлов в отслеживаемых каталогах в режиме реального времени через WinAPI.
3. **Движок глубокой диагностики процессов (`DeepDiagnosticsEngine`):**
   * Потоковый и периодический анализ утечек ресурсов: дескрипторов (`handles_count`), объектов GDI/USER, обращений к странице подкачки (`Page Faults`).
   * Поведенческая форензика: мониторинг активного фокусного окна, радар доступа приложений к веб-камере и микрофону, парсинг реестра `UserAssist`.
   * Качество ядра: латентность прерываний DPC/ISR, термический троттлинг (`PROCHOT`) и дампы падений системы (BSOD Minidumps).

## 5. Режимы работы и оптимизация ресурсов

Сервис телеметрии (`main.py` / `TelemetryLoggerService`) поддерживает 3 режима сбора:

1. **`minimal` (Ультралегковесный):**
   * **Частота:** 5,0 сек (или заданный `--interval`).
   * **Нагрузка:** ~28 мс времени ЦП за замер, ~120 МБ RAM, 0% постоянной загрузки ЦП.
   * **Сбор:** Только быстрые метрики ЦП, ОЗУ, GPU, I/O дисков, сети и Топ-N процессов.
2. **`hybrid` (Адаптивный гибридный — режим по умолчанию):**
   * **Быстрый цикл (5,0 с):** Базовые метрики.
   * **Тяжелый цикл (60–300 с):** Периодический опрос тяжелых провайдеров (LibreHardwareMonitor, SMART дисков, сетевых пингов).
3. **`full` (Полный стек):**
   * **Частота:** Запрос всех тяжелых сенсоров и провайдеров LHM на каждом тике.

## 6. База данных, ротация и агрегация (SQLite Rollups)

Все данные сохраняются в базу данных SQLite (`telemetry.db`) в режиме **WAL (Write-Ahead Logging)**:

* **`system_snapshots`** — системные срезы ЦП, ОЗУ, GPU, дискового I/O, сети и Uptime.
* **`process_snapshots`** — Топ-N процессов с деталями по ресурсам.
* **`sensor_polls`** — нормализованные замеры всех аппаратных датчиков LHM/WinAPI.
* **`telemetry_events`** — события PnP, файловые операции, тревоги и аномалии.

### Агрегация и очистка (Rollup Engine)
Для предотвращения разрастания базы данных активированы автоматические процедуры:
1. **2-минутный rollup (`aggregate_process_metrics_2min`):** Данные процессов старше 2 минут обобщаются в 2-минутные средние значения.
2. **Суточный rollup (`aggregate_process_metrics_daily`):** Данные старше 24 часов сводятся в дневные агрегаты с сохранением пиковых выбросов.
3. **Ротация данных (`cleanup_old_records`):** Автоматическое удаление сырых записей старше 7 дней.
