# Дорожная карта развития подсистемы телеметрии Windows (TELEMETRY_ROADMAP.md)

Подсистема телеметрии **AI-Breadboard Apps Windows Telemetry** представляет собой специализированный локальный движок глубокого мониторинга, форензики ядра и поведенческого анализа процессов в операционной среде Windows. Настоящая дорожная карта определяет техническую стратегию, архитектурные модернизации, расширения спектра собираемых метрик и план оптимизации производительности хранилища на 2026–2027 годы.

---

## 1. Системный контекст и базовое состояние архитектуры

Текущая архитектура движка строится на гибридном сочетании асинхронного опроса оборудования, нативных Win32/NTDLL FFI-биндингов и низкоуровневой трассировки событий ядра. Анализ исходного кода показывает наличие устойчивого фундамента, включающего ключевые компоненты:

* **Модуль сбора системных метрик (`SystemCollector`)**: Обеспечивает асинхронную сборку снимков системы (`SystemSnapshot`) с использованием `asyncio.gather`. Отвечает за идентификацию хоста (`get_system_identity`), срез процессора (`get_cpu_metrics`), памяти, видеокарт (`GpuProber`), открытых TCP/UDP сокетов (`get_listening_ports`) и сетевого трафика программ (`get_process_network_activity`).
* **Движок глубокой форензики (`DeepDiagnosticsEngine`)**: Выполняет прямой опрос нативных интерфейсов Windows (`kernel32`, `user32`, `psapi`) для детекции утечек дескрипторов (Handles), GDI/USER объектов (`collect_process_leaks`), измерения задержек DPC/ISR прерываний ядра, фиксации троттлинга (`collect_kernel_throttling`) и анализа истории активности (`UserAssist`).
* **Подсистема событийной трассировки (`AIW64ETWCollector` & `AIW64Collector`)**: Осуществляет мониторинг файловой системы, веток реестра и событий аудита безопасности ядра (Event ID 4688 — запуск процессов, Event ID 4663 — доступ к объектам, Event ID 5156/5158 — сетевой фильтр WFP, Event ID 4657 — модификация реестра).
* **Стек дисковой телеметрии (`WindowsStorageUsageCollector`)**: Реализует 4-уровневую модель взаимодействия с дисками: от общего инвентаря томов до прямого снятия показателей NVMe SMART, износа Wear Leveling и попроцессного I/O.
* **Транзакционное хранилище SQLite (`TelemetryStorage`)**: Использует режим WAL (Write-Ahead Logging), двухуровневую буферизацию (`TelemetryBuffer`) и фоновый агрегатор (`TelemetrySqlAggregator`) для ведения многоуровневых роллапов (`hourly`, `daily`, `weekly`, `monthly`).
* **Безопасность и контекст выполнения (`ProcessTokenCollector`)**: Извлекает маркеры доступа процессов, права UAC (Elevation), уровни целостности (Integrity Level) и SID пользователей.
* **Сенсор нестабильности периферии (`DeviceFlappingSensor`)**: Отслежвает дребезг и циклические переподключения PnP/USB-устройств.

Несмотря на высокий уровень проработки, существующая реализация имеет резервы для расширения глубины сбора данных, минимизации накладных расходов на CPU/RAM и усиления возможностей автоматического выявления аномалий.

## 2. Стратегические векторы модернизации

Развитие подсистемы телеметрии фокусируется на четырех независимых, но взаимосвязанных направлениях:

1. **Расширение горизонтов сбора данных (Data Coverage)**: Интеграция узкоспециализированных провайдеров событий ядра, расширенный аудит скриптовых движков, трассировка сетевых пакетов на уровне провайдера и глубокая инвентаризация аппаратного обеспечения.
2. **Продвинутая форензика и динамический сэмплинг (Advanced Forensics)**: Построение персистентных графов происхождения процессов, локализация источников задержек ядра до конкретного файла драйвера и адаптивное управление частотой опроса при инцидентах.
3. **Оптимизация производительности и хранилища (Performance & Storage)**: Полное устранение блокирующих вызовов WMI, оптимизация структуры SQL-индексов, внедрение строгих лимитов RAM для кольцевых буферов и асинхронный сброс данных.
4. **Замкнутый AI-контур и самовосстановление (Autonomous AI Loop)**: Интеграция телеметрических срезов с эвристическими правилами `DiagnosticsEngine`, генерация машиночитаемых контекстов для LLM и исполнение защищенных сценариев устранения проблем (`RemediationAction`).

## 3. Детализированная фазировка реализации

### 3.1. Фаза 1: Расширение источников и глубина сбора данных

Главная цель первой фазы — устранение «слепых зон» мониторинга и привлечение специализированных источников событий Windows.

#### 1. Подключение провайдеров Sysmon и Script Block Logging
С использованием вызовов `WevtAPI` (`wevtapi.dll`) расширяется список опрашиваемых каналов событий Windows Event Log:
* Подписка на канал `Microsoft-Windows-Sysmon/Operational`:
  * **Event ID 1**: Запуск процессов с вычислением криптографических хэшей (MD5, SHA256, IMPHASH).
  * **Event ID 7**: Загрузка модулей и DLL в адресное пространство процессов (детекция DLL Side-Loading).
  * **Event ID 10**: Обращения к памяти чужих процессов (`ProcessAccess`, выявление дампов LSASS и Process Injection).
  * **Event ID 11 / 23 / 26**: Создание и удаление файлов с фиксацией хэшей.
* Подписка на канал `Microsoft-Windows-PowerShell/Operational`:
  * **Event ID 4104**: Декодирование и запись полных блоков выполняемых скриптов PowerShell (`Script Block Logging`), включая обфусцированные команды.

#### 2. Интеграция анализа сетевого трафика (DPI & LAN)
Расширяется связка модулей `TSharkWrapper`, `TrafficAnalyzer`, `WindowsNetworkUsageCollector` и `WindowsLanScanner`:
* Перевод `WindowsLanScanner` на постоянный фоновый опрос таблицы ARP (`GetIpNetTable2` из `iphlpapi.dll`) для моментального обнаружения новых устройств в сегменте LAN.
* Внедрение автоматического снятия кратковременных дампов трафика (pcap) при детекции сетевых всплесков модулем `IncidentDetector` с последующим анализом протоколов через `TrafficAnalyzer`.

#### 3. Расширенный опрос аппаратных датчиков и драйверов
* Добавление провайдера `CpuzAidaProber` и чтения JSON-экспорта утилиты HWiNFO (`HWiNFO64.exe -j`) для извлечения напряжений VRM, суб-таймингов памяти и лимитов мощности GPU/CPU.
* Использование `SetupAPI` (`setupapi.dll`) для инвентаризации устаревших пакетов драйверов в `DriverStore` (`pnputil.exe /enum-drivers`) и автоматической фиксации кодов ошибок PnP-устройств (Code 10/43/28).

---

### 3.2. Фаза 2: Продвинутая форензика и динамический адаптивный сэмплинг

Вторая фаза направлена на превращение сухих метрик в причинно-следственные связи и граф системных событий.

#### 1. Построение графа происхождения процессов (Process Provenance Graph)
Формирование персистентного дерева цепочек запуска процессов в базе данных SQLite (таблица `process_provenance_events`):
* Сохранение уникальных GUID процессов (`process_guid`), идентификаторов родителей (`parent_guid`), токенов безопасности UAC (`ProcessTokenCollector`), хэшей и полных командных строк.
* Сохранение исторического графа даже после завершения процесса-родителя, что позволяет расследовать атаки типа Living off the Land (LotL).

#### 2. Локализация источников DPC/ISR прерываний ядра
Расширение возможностей модуля `DeepDiagnosticsEngine`:
* При обнаружении высокого уровня задержек DPC/ISR (`dpc_status == 'severe'`) запускается сэмплирование профиля ядра через ETW (`ETW SampledProfileTrace`).
* Автоматическое определение конкретного файла драйвера `.sys`, вызывающего задержки прерываний (например, сбойные сетевые или графические драйверы).

#### 3. Гиперадаптивный сэмплинг при инцидентах (`SamplingController`)
* Автоматический перевод `SamplingController` из режима `NORMAL` в режим `INCIDENT` или `FORENSIC` при срабатывании триггеров `IncidentDetector` (CPU Spike, Disk Burst, Defender Alert).
* В режиме `FORENSIC` частота опроса базовых метрик увеличивается до 100–250 мс, а снимки кольцевого буфера `TelemetryRingBuffer` дампируются в таблицу `incidents` базы данных SQLite с временным окном 5 минут *до* и 2 минуты *после* аномалии.

---

### 3.3. Фаза 3: Высокопроизводительный профиль и оптимизация хранения

Третья фаза решает задачи снижения нагрузки на ЦП, оптимизации объема занимаемой памяти RAM и ускорения дискового ввода-вывода.

#### 1. Полный отказ от синхронных COM/WMI вызовов
В текущей версии `SystemCollector` отдельные операции (например, опрос спецификаций планок памяти `Win32_PhysicalMemory`) задействуют COM-объект `win32com.client`.
* Полный перевод всех обращения к информации о системе и железе на нативные FFI-структуры (`kernel32`, `ntdll`, `setupapi`) или асинхронный фоновый воркер `com_worker`.
* Исключение вероятности зависания главного событийного цикла Python при сбоях подсистемы WMI.

#### 2. Оптимизация индексов и агрегации в SQLite
В подсистеме `TelemetryStorage`:
* Добавление составных покрывающих индексов в `schema.py` для ускорения аналитических выборок:
  * `CREATE INDEX IF NOT EXISTS idx_snapshots_created_host ON system_snapshots(created_at, hostname);`
  * `CREATE INDEX IF NOT EXISTS idx_rollups_sensor_bucket ON telemetry_rollups(sensor_id, bucket_start, level);`
* Перевод выполнения каскадного пайплайна агрегации `TelemetrySqlAggregator` (`raw -> hourly -> daily`) на фоновый регламентный поток с регулируемым квантом времени.

#### 3. Динамические лимиты RAM для кольцевых буферов
* Введение жесткого байтового лимита оперативной памяти для классов `TelemetryRingBuffer` и `TelemetryBuffer` (например, не более 32 МБ RAM).
* Автоматический сброс залежавшихся записей на диск или вытеснение старых сэмплов при достижении порога памяти.

---

### 3.4. Фаза 4: Замкнутый AI-контур и самовосстановление системы

Заключительная фаза интегрирует подсистему телеметрии с автономными агентами диагностики и административными инструментами.

#### 1. Синтез данных с эвристическим движком (`DiagnosticsEngine`)
* Автоматическая передача текущего снимка `SystemSnapshot` и результатов аудитов в движок `DiagnosticsEngine` для прохождения каталога проверок (`proc_001`–`proc_015`, `mem_001`–`mem_008`, `drv_001`–`drv_007`, `net_001`–`net_006`).
* Автоматический расчет интегрального индекса здоровья системы (`Health Score` от 0 до 100).

#### 2. Машиночитаемые контексты для LLM-агентов
* Использование встроенного метода `format_incident_markdown_for_llm` в `IncidentDetector` для формирования структурированных Markdown-промптов.
* Передача полного контекста аномалии (метрики до/после, подозрительные процессы, связанные события ETW) локальной нейросетевой модели без нерелевантного «шума».

#### 3. Исполнение безопасных сценариев устранения (`RemediationAction`)
* Формирование атомарных рекомендаций по исправлению найденных проблем (очистка временных каталогов `CleanCollector`, перезапуск зависших служб, включение защиты Defender).
* Выполнение исправлений через изолированный фасад с подтверждением прав администратора.

## 5. Метрики эффективности и целевые KPI

Успешность выполнения дорожной карты оценивается по следующим целевым показателям производительности и качества:

1. **Ресурсоемкость демона телеметрии**:
   * Нагрузка на ЦП в фоновом режиме `NORMAL`: **< 0.5%** одного ядра CPU.
   * Потребление оперативной памяти RAM: **< 25-32 МБ** (включая все кольцевые буферы с лимитом `max_bytes=32MB`).
   * Интенсивность записи на диск: **< 100 КБ/сек** благодаря транзакционной буферизации в SQLite и WAL-режиму.
2. **Скорость реакции и глубина детекции**:
   * Время фиксации аномалии с момента возникновения: **< 500 мс** (в режиме `FORENSIC` — 250 мс).
   * Полнота данных в инциденте: **100%** связка с процессами-виновниками и фрагментом кольцевого буфера.
   * Время выполнения асинхронного системного снимка `get_snapshot()`: **< 0.3 сек**.
3. **Надежность и автономность хранилища**:
   * Максимальный объем базы данных `telemetry.db`: Автоматическое удержание в пределах установленного лимита (по умолчанию **100 МБ**).
   * Доступность SQLite хранилища: **99.99%** утилизации без повреждений WAL-журнала при внезапных перезагрузках или падениях питания благодаря `PRAGMA synchronous = NORMAL` и `PRAGMA busy_timeout = 15000`.
