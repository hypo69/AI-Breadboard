# Техническое задание: Подсистема точечного версионирования файлов на базе Windows VSS и двухрежимного хранилища (Two-Tiered Version Store)

## 1. Назначение подсистемы и ключевые принципы

Настоящее техническое задание определяет архитектуру и порядок реализации подсистемы мгновенного и долговременного версионирования файлов для платформы **«Интеллектуальный центр тонких настроек операционной системы и телеметрии параметров ОС»**.

Ключевая проблема классических систем резервного копирования файлов заключается в высоком расходе дискового ввода-вывода и памяти при частой фиксации промежуточных состояний крупных документов или конфигурационных файлов. Подсистема версионирования решает эту задачу за счет использования нативных механизмов службы теневого копирования томов Windows (**Volume Shadow Copy Service, VSS**) в сочетании с двухуровневой архитектурой хранения (**Two-Tiered Version Store**).

### Ключевые архитектурные принципы

* **Zero-Copy Instant Versioning**: При выполнении команды фиксации версии физическое копирование файла на диске не производится. Система инициирует мгновенный снимок тома средствами VSS, фиксируя точечный срез файловой системы на физическом уровне с нулевым временем ожидания со стороны пользователя.
* **Двухуровневое хранение (Two-Tiered Version Store)**: Разделение версий на оперативный горячий слой (**Hot VSS Layer**), опирающийся на точки восстановления тома, и долгосрочный холодный слой (**Cold Persistent Store**), использующий локальную базу данных SQLite и сжатые бинарные блобы.
* **Автономное управление через WMI/CIM**: Исключение сложных COM-обвязок `IVssBackupComponents` в пользу вызовов WMI-класса `Win32_ShadowCopy`, что обеспечивает производительную и надежную работу исполнительного модуля непосредственно из среды Python без сторонних зависимостей.
* **Сквозная интеграция с Command Registry**: Реализация провайдера `WindowsVersionProvider` с поддержкой единого CLI-интерфейса и REST API эндпоинтов для взаимодействия с веб-панелью.

## 2. Низкоуровневые механизмы Windows VSS и WMI-интеграция

Служба VSS работает на уровне всей файловой системы NTFS/ReFS и создает точки восстановления для тома целиком. Для извлечения и версионирования конкретного файла подсистема транслирует локальный путь файла в точечный доступ внутри структуры теневой копии.

### 2.1 Создание теневой копии через WMI

Для создания снимка тома подсистема вызывает системный метод `Create` WMI-класса `Win32_ShadowCopy` в пространстве имен `root\cimv2`.

Ниже приведен пример использования системной команды создания снимка тома через CIM-интерфейс:

```powershell
$shadow = Invoke-CimMethod `
    -ClassName Win32_ShadowCopy `
    -MethodName Create `
    -Arguments @{
        Volume = 'C:\'
        Context = 'ClientAccessible'
    }

$shadow.ShadowID
```

Параметры вызова метода `Win32_ShadowCopy.Create`:
* `Volume` — буква или GUID-путь целевого тома (например, `C:\`).
* `Context` — режим контекста теневой копии (`ClientAccessible` для доступа пользователем или `Backup` для системных операций).

После выполнения команды операционная система возвращает идентификатор созданного снимка `ShadowID` и системное имя устройства вида `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyXX`.

### 2.2 Доступ к файлу внутри VSS Snapshot

Для чтения файла из созданного снимка используются два взаимодополняющих механизма:
1. **Прямой адрес через Device Path**: Префикс пути вида `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy42\Data\config.json` позволяет считывать фиксированную версию файла напрямую из пространства ядра Windows.
2. **Монтирование снимка (ExposeSnapshot)**: Для открытого просмотра файлов снимок экспонируется как виртуальный символический путь или монтируется в локальную папочную структуру с доступом только для чтения через системную процедуру `ExposeSnapshot`.

## 3. Двухуровневая архитектура хранилища версий

Для предотвращения переполнения дискового пространства и защиты от авто-удаления снимков службой Windows подсистема реализует гибридную двухслойную модель удержания данных.

### 3.1 Сравнение слоев хранения версий

Ниже приведено распределение ответственности и функциональных характеристик между горячим и холодным слоем хранилища версий.

| Параметр | Горячий слой (Hot VSS Layer) | Холодный слой (Cold Persistent Store) |
| :--- | :--- | :--- |
| **Физический механизм** | VSS Snapshots (`Win32_ShadowCopy`) | База данных SQLite (`telemetry.db`) + Zstandard/ZIP Blobs |
| **Скорость создания** | Мгновенно (<10 мс, без копирования) | Зависит от размера файла (копирование и сжатие) |
| **Занимаемое место** | Дифференциальные блоки на томе NTFS | Отдельное сжатое дедуплицированное хранилище |
| **Срок хранения** | Оперативный (до 24 часов) | Долгосрочный (30 дней / бессрочно) |
| **Автономия** | Может удаляться ОС при нехватке места | Полный контроль со стороны приложения |

### 3.2 Политика удержания и миграции (Retention Policy)

Автоматический фоновый планировщик подсистемы управляет жизненным циклом созданных версий по следующему регламенту:
1. **Первые 24 часа**: Версия сохраняется исключительно в виде теневой копии VSS (Hot Layer). Чтение и восстановление выполняются с мгновенным откликом.
2. **От 24 часов до 30 дней**: Фоновый процесс выгружает тело файла из VSS снимка, сжимает его алгоритмом Zstandard, вычисляет контрольную сумму SHA-256 и сохраняет в таблицу хранилища блобов SQLite, после чего освобождает устаревший VSS снимок.
3. **Старше 30 дней / 1 года**: Версии консолидируются в долговременный сжатый архив либо удаляются согласно правилам лимитов хранилища.

## 4. Схема базы данных SQLite (`telemetry.db`)

Для учета созданных версий, привязки к снимкам VSS и хранения долговременных бинарных копий в базу данных `telemetry.db` добавляются две специализированные таблицы.

```sql
-- Таблица метаданных зарегистрированных версий файлов
CREATE TABLE IF NOT EXISTS file_versions (
    version_id INTEGER PRIMARY KEY AUTOINCREMENT,
    file_path TEXT NOT NULL,
    volume_letter TEXT NOT NULL,
    snapshot_id TEXT,
    snapshot_device_path TEXT,
    storage_layer TEXT NOT NULL DEFAULT 'VSS', -- 'VSS', 'PERSISTENT_BLOB', 'ARCHIVED'
    blob_id TEXT,
    file_size_bytes INTEGER NOT NULL,
    sha256_hash TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    description TEXT
);

-- Таблица долгосрочного хранения бинарных блобов файлов
CREATE TABLE IF NOT EXISTS file_version_blobs (
    blob_id TEXT PRIMARY KEY,
    compressed_payload BLOB NOT NULL,
    original_size_bytes INTEGER NOT NULL,
    compressed_size_bytes INTEGER NOT NULL,
    compression_algorithm TEXT NOT NULL DEFAULT 'zstd',
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_file_versions_path ON file_versions(file_path);
CREATE INDEX IF NOT EXISTS idx_file_versions_hash ON file_versions(sha256_hash);
```

## 5. Алгоритмы работы ключевых операций (`WindowsVersionProvider`)

Подсистема предоставляет единый класс `WindowsVersionProvider`, реализующий базовый набор атомарных операций управления версиями.

### 5.1 Операция сохранения версии (`version save`)

1. **Прием запроса**: Прием пути файла (например, `C:\Data\config.json`).
2. **Определение тома**: Извлечение целевого тома (`C:\`).
3. **Запрос к WMI**: Инициализация вызова `Win32_ShadowCopy.Create` для тома `C:\`.
4. **Фиксация снимка**: Получение `ShadowID` и `snapshot_device_path`.
5. **Расчет контрольной суммы**: Вычисление хеша SHA-256 текущего файла для контроля целостности.
6. **Запись метаданных**: Внесение записи в таблицу `file_versions` с пометкой `storage_layer: 'VSS'`.

### 5.2 Операция восстановления версии (`version restore`)

1. **Поиск записи**: Чтение метаданных версии из `file_versions` по `version_id`.
2. **Проверка слоя хранения**:
   * Если `storage_layer == 'VSS'`: Проверяется доступность устройства `snapshot_device_path`. Чтение файла осуществляется по пути `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyXX\Data\config.json`.
   * Если `storage_layer == 'PERSISTENT_BLOB'`: Извлекается запись из `file_version_blobs`, выполняется декомпрессия сжатого полезного содержимого в память.
3. **Валидация целостности**: Сверка вычисленного хеша восстановленных данных с записанным значением `sha256_hash`.
4. **Атомарная замена**: Запись полученных данных в целевой файл `C:\Data\config.json` с предварительным созданием страховой копии.

### 5.3 Операция просмотра историй (`version list`)

Запрос к базе данных `file_versions` по целевому пути файла с возвратом полного списка сохраненных точечных версий, содержащего метки времени UTC, размеры, хеши и текущий слой хранения.

## 6. Требования к безопасности и правам доступа

Работа с подсистемой теневого копирования требует строгого соблюдения полномочий операционной системы.

### 6.1 Системные привилегии

Для вызова методов `Win32_ShadowCopy` и чтения файлов из каталогов `GLOBALROOT` процессу приложения требуются права администратора (**Administrator Integrity Level**) и активные привилегии резервного копирования:
* `SeBackupPrivilege` — право чтения любых файлов в системе в обход стандартных списков ACL.
* `SeRestorePrivilege` — право записи и восстановления файлов с заменой системных дескрипторов безопасности.

При отсутствии административных прав метод WMI или вызов `AddToSnapshotSet` возвращает ошибку отказа в доступе `E_ACCESSDENIED`. В этом случае подсистема автоматически переключается на резервный режим работы (**Fallback Mode**), выполняя прямое копирование файла в холодный слой `file_version_blobs` без создания снимка VSS.

## 7. REST API Контракт (FastAPI)

Для интеграции с веб-интерфейсом подсистема предоставляет следующие эндпоинты.

### 7.1 `POST /api/v1/versions/save`
Создание мгновенной версии файла.

**Тело запроса**:
```json
{
  "file_path": "C:\\Data\\config.json",
  "description": "Ручное сохранение конфигурации перед правкой"
}
```

**Ответ**:
```json
{
  "status": "success",
  "version_id": 42,
  "storage_layer": "VSS",
  "snapshot_id": "{7C3A8B12-9D0E-4F12-B345-6789ABCDEF01}",
  "created_at": "2026-10-06T11:35:00Z",
  "sha256": "a83c9b102e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b"
}
```

### 7.2 `GET /api/v1/versions/list`
Получение списка всех зарегистрированных версий указанного файла.

### 7.3 `POST /api/v1/versions/restore`
Восстановление выбранной версии файла по `version_id`.
