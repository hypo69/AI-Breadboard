### Основные директории и их назначение

## Быстрый старт

### Конфигурационные файлы

Система документации использует несколько конфигурационных файлов:

- **`docs/ru/conf.py`** — конфигурация Sphinx для сборки документации
- **`.readthedocs.yml`** — конфигурация для платформы Read the Docs
- **`.github/workflows/docs.yml`** — GitHub Actions workflow для CI/CD
- **`docs/ru/requirements-docs.txt`** — зависимости для сборки

### Установка зависимостей

Для работы с документацией установите зависимости:

```bash
pip install -r docs/ru/requirements-docs.txt
```

Этот файл содержит:
- **Sphinx** — генератор документации
- **sphinx-rtd-theme** — профессиональная тема Read the Docs
- **myst-parser** — поддержка Markdown
- **sphinx-autodoc-typehints** — автоматизация документирования типов
- **markdownlint-cli2** — валидация Markdown
- **linkchecker** — проверка ссылок
- И другие утилиты

### Первая локальная сборка

Соберите документацию локально:

```bash
# Полная сборка с валидацией
make docs-build

# Или вручную через Python
sphinx-build -b html docs/ru docs/ru/_build/html
```

После сборки результаты появятся в `docs/ru/_build/html/`

### Запуск локального сервера

Просмотрите документацию в браузере:

```bash
# Запустить HTTP-сервер
make docs-serve

# Сервер будет доступен по адресу http://localhost:8000
```

### Автоматическая пересборка при разработке

Для удобства разработки используйте режим наблюдения:

```bash
# Автоматически пересобирает при изменении файлов
make docs-watch

# Это также запустит локальный сервер на http://localhost:8000
```

Документируйте Python код в формате Google-style для автогенерации:

def calculate_factorial(n: int) -> int:
    """Вычисляет факториал числа.

    Функция использует рекурсивный алгоритм для вычисления факториала.
    Результаты кэшируются для оптимизации производительности.

    Args:
        n: Целое число, для которого нужно вычислить факториал.
           Должно быть неотрицательным целым числом.

    Returns:
        Факториал числа n. Например, для n=5 вернёт 120.

    Raises:
        ValueError: Если n отрицательное число.
        TypeError: Если n не целое число.

    Example:
        >>> calculate_factorial(5)
        120

        >>> calculate_factorial(0)
        1

    Note:
        Функция оптимизирована для чисел до 1000.
        Для больших чисел рекомендуется использовать библиотеку math.

    See Also:
        math.factorial: Встроенная реализация в стандартной библиотеке
        itertools.permutations: Для работы с перестановками
    """
    if not isinstance(n, int):
        raise TypeError(f"n должно быть целым числом, получено {type(n)}")
    
    if n < 0:
        raise ValueError(f"n должно быть неотрицательным, получено {n}")
    
    if n == 0 or n == 1:
        return 1
    
    return n * calculate_factorial(n - 1)

        _initialized (bool): Флаг инициализации менеджера.

## Команды разработки

### Полный список команд через Make

Используйте `Makefile` для быстрого запуска команд:

```bash
# Полная сборка документации
make docs-build

# Запуск локального HTTP-сервера для просмотра
make docs-serve

# Наблюдение за файлами и автоматическая пересборка
make docs-watch

# Только валидация структуры и синтаксиса
make docs-validate

# Только генерация API-документации из docstrings
make docs-api

# Очистка артефактов сборки
make docs-clean
```

### Детальное описание команд

#### `make docs-build` — Полная сборка

```bash
make docs-build
```

**Что происходит:**
1. Установка/обновление зависимостей из `docs/ru/requirements-docs.txt`
2. Запуск `scripts/docs/generate_api.py` для генерации API-документации
3. Запуск `scripts/docs/validate_structure.py` для проверки структуры
4. Запуск `scripts/docs/check_links.py` для проверки ссылок
5. Сборка Sphinx с параметрами `-W` (ошибки прерывают сборку) и `-j auto` (параллельная обработка)

**Результат:**
- Скомпилированная HTML документация в `docs/ru/_build/html/`
- Отчёты валидации в консоли
- Список ошибок (если есть)

**Когда использовать:**
- Перед коммитом для полной проверки
- Для финальной валидации перед публикацией
- При подготовке PR

#### `make docs-serve` — Запуск локального сервера

```bash
make docs-serve
```

**Предусловия:**
- Документация должна быть собрана (запустите `make docs-build`)

**Что происходит:**
1. Запуск Python HTTP-сервера на порту 8000
2. Сервирование файлов из `docs/ru/_build/html/`

**Результат:**
- Документация доступна по адресу `http://localhost:8000`
- Нажмите `Ctrl+C` для остановки сервера

**Когда использовать:**
- Для просмотра собранной документации
- Для проверки вёрстки и навигации
- Для внутреннего тестирования перед публикацией

#### `make docs-watch` — Автоматическая пересборка

```bash
make docs-watch
```

**Что происходит:**
1. Запуск fswatch для отслеживания изменений в `docs/ru/`
2. При обнаружении изменений автоматически запускается пересборка
3. Одновременно запускается локальный HTTP-сервер
4. Live reload при изменении файлов

**Результат:**
- Автоматическая пересборка при каждом сохранении файла
- Документация доступна по адресу `http://localhost:8000`
- Отчёты об ошибках в консоли в реальном времени

**Когда использовать:**
- Основной режим во время разработки документации
- Для быстрой обратной связи при редактировании
- При написании новых страниц

#### `make docs-validate` — Только валидация

```bash
make docs-validate
```

**Что происходит:**
1. Запуск `scripts/docs/validate_structure.py` — проверка структуры
2. Запуск `scripts/docs/check_links.py` — проверка ссылок
3. Валидация Markdown синтаксиса через markdownlint-cli2

**Результат:**
- Отчёт об ошибках и предупреждениях
- Не требует сборки Sphinx
- Быстрая проверка перед коммитом

**Когда использовать:**
- Для быстрой проверки перед коммитом
- Перед отправкой PR
- Для проверки синтаксиса после редактирования

#### `make docs-api` — Только генерация API

```bash
make docs-api
```

**Что происходит:**
1. Запуск `scripts/docs/generate_api.py`
2. Парсинг всех Python-файлов с docstrings
3. Генерация Markdown файлов в `docs/ru/api/`
4. Обновление индекса API

**Результат:**
- Обновлённые файлы в `docs/ru/api/*.md`
- Готово к включению в следующую сборку

**Когда использовать:**
- После обновления docstrings в коде
- Для регенерации API-документации перед публикацией
- При добавлении новых модулей

#### `make docs-clean` — Очистка артефактов

```bash
make docs-clean
```

**Что происходит:**
1. Удаление директории `docs/ru/_build/`
2. Удаление кэшей Python (`.pytest_cache`, `__pycache__`)
3. Очистка временных файлов

**Результат:**
- Чистое состояние репозитория
- Готово к полной пересборке

**Когда использовать:**
- Перед стартом свежей сборки
- При возникновении странных ошибок кэша
- Перед публикацией финального релиза

## API-документация

### Как работает автогенерация

Система автоматически создаёт документацию API из Python docstrings:

```
Исходный код Python
    ↓
    └─ Содержит docstrings в Google-style формате
    
Скрипт scripts/docs/generate_api.py
    ↓
    ├─ Парсит Python AST
    ├─ Извлекает классы, функции, методы
    ├─ Читает Google-style docstrings
    └─ Создаёт структурированные Markdown
    
Markdown файлы в docs/ru/api/
    ↓
    ├─ skills.md
    ├─ agents.md
    ├─ core.md
    └─ utils.md
    
Сборка Sphinx
    ↓
    └─ HTML документация с API-ссылками
```

### Когда API-документация обновляется

API-документация автоматически обновляется в следующих случаях:

1. **При локальной разработке:**
   - Запуск `make docs-api` вручную
   - При `make docs-watch` (если обнаружены изменения в коде)
   - При `make docs-build` (обновляется в рамках полной сборки)

2. **При загрузке в репозиторий (CI/CD):**
   - GitHub Actions workflow `docs.yml` запускает генерацию
   - Проверяет что API-документация синхронизирована с кодом
   - Выдаёт предупреждение если документация требует обновления

3. **Перед публикацией на Read the Docs:**
   - Сборка на Read the Docs запускает генерацию API
   - Финальная API-документация включается в опубликованный сайт

### Как добавить docstring

#### Для функции

Используйте Google-style docstring:

```python
def create_skill(name: str, description: str, handlers: Dict[str, Callable]) -> Skill:
    """Создаёт новый навык для системы.

    Функция регистрирует новый навык с указанными обработчиками
    и добавляет его в центральный реестр навыков.

    Args:
        name: Уникальное имя навыка в формате kebab-case.
              Примеры: "web-search", "pdf-parser", "email-sender".
        description: Подробное описание функциональности навыка.
                    Будет отображаться в документации и UI.
        handlers: Словарь обработчиков вида {event_type -> callable}.
                 Ключи: 'on_init', 'on_execute', 'on_cleanup', 'on_error'.

    Returns:
        Объект созданного навыка типа Skill.
        Содержит информацию о регистрации и статусе.

    Raises:
        ValueError: Если имя навыка не соответствует формату.
        KeyError: Если задан неизвестный тип обработчика.
        TypeError: Если обработчик не является callable.

    Example:
        >>> def on_execute(input_data):
        ...     return {"result": len(input_data)}
        >>> 
        >>> skill = create_skill(
        ...     name="text-length",
        ...     description="Вычисляет длину текста",
        ...     handlers={"on_execute": on_execute}
        ... )
        >>> print(skill.name)
        'text-length'

    Note:
        Навыки должны быть зарегистрированы перед использованием.
        После регистрации они доступны всем агентам в системе.

    See Also:
        SkillRegistry.register: Для явной регистрации навыка.
        Skill class: Для понимания структуры навыка.
    """
    pass
```

## CI/CD и публикация

### GitHub Actions Workflow

При каждом push в репозиторий автоматически запускается workflow для документации.

#### Что происходит в workflow

```yaml
# Запускается при:
# - push в ветки main или develop
# - pull request в main ветку
# - если изменены файлы в docs/ru/ или src/

jobs:
  validate:           # Валидирует Markdown и структуру
  generate-api:       # Генерирует API-документацию
  build:              # Собирает Sphinx документацию
  notify:             # Отправляет уведомления при ошибках
```

**Файл конфигурации:** `.github/workflows/docs.yml`

### Как проверяется документация в PR

При создании Pull Request с изменениями документации:

1. **Автоматическая проверка структуры**
   - Проверяются обязательные файлы
   - Проверяются обязательные разделы
   - Валидируется Markdown синтаксис

2. **Генерация API-документации**
   - Запускается парсинг docstrings
   - Проверяется что документация актуальна
   - Выдаётся предупреждение если нужна генерация

3. **Проверка ссылок**
   - Все внутренние ссылки проверяются
   - Ошибочные ссылки блокируют PR

4. **Сборка Sphinx**
   - Пробуется собрать полную документацию
   - Любые ошибки сборки блокируют PR
   - Артефакты сохраняются для просмотра

5. **Статус проверок**
   - Зелёная галочка ✓ если все проверки пройдены
   - Красный крест ✗ если есть ошибки
   - Можно просмотреть детали каждой проверки

### Как публикуется на Read the Docs

#### Автоматическая публикация

```
GitHub Push (в main ветку)
    ↓
GitHub Actions успешно завершается
    ↓
Read the Docs webhook активируется
    ↓
Read the Docs запускает сборку
    ↓
Sphinx собирает документацию
    ↓
HTML публикуется на readthedocs.io
    ↓
Документация доступна в интернете
```

**Файл конфигурации для Read the Docs:** `.readthedocs.yml`

#### Конфигурация Read the Docs

```yaml
version: 2

# Python для сборки
python:
  version: "3.10"
  install:
    - requirements: docs/ru/requirements-docs.txt

# Конфигурация Sphinx
sphinx:
  configuration: docs/ru/conf.py
  fail_on_warning: true

# Версионирование
versions:
  active: latest
```

#### Публикация разных версий

- **latest** — документация из ветки `main`
- **stable** — документация из последнего релиза
- **development** — документация из ветки `develop`

Каждая версия имеет собственный URL:
- `https://ai-breadboard.readthedocs.io/ru/latest/` — последняя версия
- `https://ai-breadboard.readthedocs.io/ru/stable/` — стабильная версия
- `https://ai-breadboard.readthedocs.io/ru/v1.0.0/` — конкретная версия

### Диагностика проблем с публикацией

Если документация не публикуется:

1. **Проверьте статус GitHub Actions**
   ```bash
   # Откройте вкладку Actions в GitHub
   # Проверьте последний workflow для docs
   ```

2. **Проверьте логи Read the Docs**
   - Откройте проект на readthedocs.io
   - Перейдите в "Builds"
   - Посмотрите логи последней сборки

3. **Проверьте локально**
   ```bash
   make docs-build
   # Если локально не собирается, то и на RTD не соберётся
   ```

4. **Проверьте конфигурацию**
   - `.readthedocs.yml` имеет правильный синтаксис
   - Пути в файле корректны
   - Зависимости указаны в `requirements-docs.txt`

5. **Проверьте вебхук**
   - Settings → Webhooks на GitHub
   - Убедитесь что вебхук Read the Docs активен
   - Попробуйте перестроить на Read the Docs вручную
