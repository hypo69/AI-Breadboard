Да. Тогда тебе нужен **накопительный RAG (Continuous / Incremental RAG)**, который постепенно собирает информацию о сотрудниках, связывает её с конкретными людьми и со временем формирует корпоративную базу знаний.

Причём я бы предложил не просто добавлять документы в векторную базу, а построить систему, которая **накапливает, структурирует, проверяет и уточняет знания о каждом сотруднике**.

# 2. Как происходит накопление информации

Допустим, в первый день система получает письмо:

> От: [a.petrov@company.com](mailto:a.petrov@company.com)
> Александр, проверь API до пятницы.

### Шаг 1. Извлечение информации

```json
{
  "source_type": "email",
  "source_id": "EMAIL-1001",
  "entities": [
    {
      "type": "person",
      "value": "a.petrov@company.com"
    }
  ],
  "facts": [
    {
      "subject": "EMP-0042",
      "predicate": "assigned_task",
      "object": "Проверка API"
    }
  ]
}
```

Система определяет сотрудника по почте и связывает событие с его `employee_id`.

### Шаг 2. Добавление в хранилище

```text
EMP-0042
   │
   └── ASSIGNED_TASK
          │
          ├── task: Проверка API
          ├── source: EMAIL-1001
          ├── date: 2026-09-21
          └── confidence: verified
```

### Шаг 3. Создание RAG-документа

Для семантического поиска можно создать документ:

```text
Employee: EMP-0042
Name: Александр Петров

On 2026-09-21:
A task related to API verification was assigned.
Source: EMAIL-1001
```

Этот текст индексируется в Vector Store.

**Но оригинальное письмо должно сохраняться отдельно.** RAG-документ является производным представлением, а не заменой источника.

# 3. Накапливать нужно не только документы, но и знания

Здесь есть существенное различие.

### Обычный RAG

```text
Документ 1 → Embedding → Vector DB
Документ 2 → Embedding → Vector DB
Документ 3 → Embedding → Vector DB
```

В итоге ты имеешь коллекцию документов.

### Твой вариант

```text
Документ 1
     │
     ▼
Факт 1 ────────┐
               │
Документ 2     ▼
     │      EMP-0042
     ▼         │
Факт 2 ────────┤
               │
Документ 3     ▼
     │      Факт 3
     ▼         │
Факт 3 ────────┘
```

Система должна объединять сведения о сотруднике из разных источников.

Например:

| Источник | Извлеченный факт             |
| -------- | ---------------------------- |
| HR       | Senior Developer             |
| Email    | Участвует в API-проекте      |
| Чат      | Помогает коллегам с Python   |
| Задачи   | Ответственный за интеграцию  |
| Встреча  | Представлял команду          |
| Документ | Автор архитектурного решения |

Эти факты не обязательно нужно превращать в окончательные утверждения о компетенциях или должностных полномочиях. Их следует хранить с источниками, датами и статусом подтверждения.

# 4. Предлагаю разделить RAG на три слоя

Для AI-Breadboard это будет более гибкая архитектура.

## Слой A. Raw Knowledge

Сохраняются исходные данные.

```text
raw_knowledge/
├── emails/
├── documents/
├── chats/
├── meetings/
└── tasks/
```

Примеры:

* оригинальные письма;
* документы;
* сообщения;
* транскрипции;
* системные события.

Здесь ничего не теряется.

---

## Слой B. Structured Knowledge

Из исходных данных извлекаются структурированные сведения.

```text
employees
employee_aliases
employee_emails
employee_phones
employee_positions

facts
relationships
projects
tasks
events
```

Пример факта:

```json
{
  "fact_id": "FACT-1001",
  "subject_id": "EMP-0042",
  "predicate": "works_on",
  "object": "Project Alpha",

  "valid_from": "2026-01-01",
  "valid_to": null,

  "source_ids": [
    "EMAIL-1001",
    "MEETING-202"
  ],

  "status": "proposed"
}
```

Здесь я бы добавил **статус факта**:

* `proposed` — извлечен автоматически;
* `confirmed` — подтвержден надежным источником или человеком;
* `rejected` — признан ошибочным;
* `superseded` — заменен более новым фактом.

Это позволяет не выдавать предположение LLM за установленную истину.

---

## Слой C. Semantic RAG

Здесь хранятся embeddings для семантического поиска.

```text
Vector Store
│
├── Employee-related documents
├── Facts
├── Conversations
├── Project context
└── Historical events
```

У каждого фрагмента должны быть метаданные:

```json
{
  "chunk_id": "CHUNK-5001",
  "employee_ids": [
    "EMP-0042"
  ],

  "source_id": "EMAIL-1001",
  "knowledge_type": "task",
  "created_at": "2026-09-21T10:30:00Z"
}
```

Это позволяет применять фильтры по сотрудникам, источникам и датам.

# 5. Важный момент: RAG должен обновляться

Представим, что сегодня сотрудник Developer, а через полгода становится Team Lead.

Новая информация поступает:

> Александр Петров назначен Team Lead.

Система должна:

1. Определить сотрудника.
2. Извлечь изменение должности.
3. Сохранить источник.
4. Добавить новую запись в историю.
5. Не удалять прежнюю должность.
6. Обновить поисковые представления.
7. При необходимости пересчитать связанные сведения.

```text
2026-01-01
    Developer
        │
        ▼
2026-07-01
    Team Lead
```

При запросе:

> «Кем был Александр в марте?»

RAG должен учитывать временной контекст.

При запросе:

> «Кто сейчас Team Lead?»

Нужна актуальная версия данных.

# 6. Как избежать бесконтрольного роста базы

Накопительный RAG может быстро разрастаться.

Поэтому я бы предусмотрел **циклическую обработку знаний**.

```text
NEW DATA
   │
   ▼
EXTRACT
   │
   ▼
RESOLVE IDENTITY
   │
   ▼
CHECK DUPLICATES
   │
   ▼
MERGE / UPDATE
   │
   ▼
INDEX
   │
   ▼
PERIODIC RE-EVALUATION
```

### Пример

Сегодня получено:

> Alex отвечает за API.

Завтра:

> Александр Петров занимается API.

Послезавтра:

> Alex из Engineering ведет API-интеграцию.

Система должна попытаться понять, относятся ли сведения к одному сотруднику, но сохранять отдельные источники и не объединять факты без достаточных оснований.

Возможные оптимизации:

* дедупликация документов;
* повторное использование embeddings;
* обновление только изменившихся фрагментов;
* архивация устаревших представлений;
* периодическая проверка противоречий.

# 7. Как LLM будет использовать накопленные знания

Допустим, ты спрашиваешь:

> «Какие задачи обычно выполняет Саша из Engineering?»

Система:

```text
1. Определяет возможных сотрудников с алиасом "Саша".
          │
          ▼
2. Уточняет личность по контексту.
          │
          ▼
3. Получает employee_id.
          │
          ▼
4. Ищет структурированные факты.
          │
          ▼
5. Выполняет семантический поиск документов.
          │
          ▼
6. Проверяет источники и актуальность.
          │
          ▼
7. Формирует контекст для LLM.
```

LLM получает:

```text
EMPLOYEE:
Александр Петров

CONFIRMED INFORMATION:
- Senior Developer
- Engineering

PROPOSED INFORMATION:
- Participates in API integration
- Reviews Python code

SOURCES:
- Email-1001
- Task-202
- Meeting-55
```

И формирует ответ с учетом статуса и источников.

# 8. Я бы добавил механизм обучения на подтверждениях

Это интересная часть твоей системы.

Предположим, RAG считает:

```text
"Alex" → EMP-0042
```

Пользователь подтверждает:

> Да, Alex — это Александр Петров.

Система может сохранить подтверждение:

```json
{
  "alias": "Alex",
  "employee_id": "EMP-0042",
  "verification": {
    "type": "human_confirmation",
    "verified_at": "2026-09-21T12:00:00Z"
  }
}
```

Но я бы не делал так, чтобы одно подтверждение автоматически связывало этот никнейм со всеми будущими упоминаниями без учета контекста. Никнеймы могут быть общими, а разные источники могут содержать ошибки.

## Мой вывод

Тебе нужен не просто Employee RAG, а **накопительная система корпоративных знаний с разрешением идентичности**.

Я бы строил её по принципу:

> **Raw Data → Identity Resolution → Structured Facts → Evidence → Vector Index → Hybrid Retrieval → LLM**

При этом важно, чтобы система сохраняла историю, источники, неопределенность и возможность исправления ошибок.

### Следующий важный вопрос

**Откуда именно будет поступать информация о сотрудниках?**

Я бы хотел уточнить это, потому что архитектура накопления сильно зависит от источников:

1. **Email** — Outlook / Exchange / Gmail?
2. **Корпоративные чаты** — Teams / Slack / WhatsApp?
3. **Документы** — PDF, Word, Excel, внутренние базы?
4. **Телефонные разговоры** — записи и транскрипции?
5. **Ручные данные** — пользователь сам рассказывает AI о сотрудниках?
6. **Все источники одновременно?**

Если ты планируешь использовать **все источники**, то следующим шагом стоит спроектировать полноценный **Knowledge Ingestion Pipeline с очередью событий, дедупликацией и инкрементальным обновлением RAG**.


Тогда я бы проектировал для тебя **универсальную корпоративную систему накопления знаний (Enterprise Knowledge Intelligence Platform)**, в которой информация из всех источников постепенно объединяется в единое хранилище, привязанное к конкретным сотрудникам.

Это уже не просто RAG для поиска документов. Это система, которая строит **динамическую карту сотрудников, их деятельности, связей и корпоративных знаний**.

# 2. Главное решение: единый Ingestion Pipeline

Не стоит создавать отдельный RAG для каждого источника.

Например:

```text
Outlook ────────┐
Teams ──────────┤
Gmail ──────────┤
PDF ────────────┤
CRM ────────────┼──► Unified Knowledge Pipeline
Audio ──────────┤
Manual Input ───┤
File System ────┘
```

Каждый источник преобразуется в единый внутренний формат.

### Унифицированное событие

```json
{
  "event_id": "EVT-10001",
  "source": {
    "type": "email",
    "system": "outlook",
    "external_id": "MSG-12345"
  },
  "event_type": "message_received",
  "occurred_at": "2026-09-21T10:30:00Z",

  "participants": [
    {
      "external_identity": "a.petrov@company.com",
      "role": "sender"
    }
  ],

  "content": {
    "text": "Проверь API до пятницы.",
    "language": "ru"
  },

  "metadata": {
    "department": "Engineering",
    "classification": "internal"
  }
}
```

Этот формат не зависит от того, поступила информация из Outlook, Teams или CRM.

# 3. Очередь событий

Поскольку данные будут поступать постоянно, обработку лучше отделить от приема.

### Например

```text
Новые сообщения
      │
      ▼
Connector
      │
      ▼
Event Queue
      │
      ├──► Identity Worker
      ├──► Document Worker
      ├──► Audio Worker
      └──► Metadata Worker
```

В качестве очереди можно рассмотреть:

| Технология     | Назначение                              |
| -------------- | --------------------------------------- |
| SQLite Queue   | Простой локальный MVP                   |
| Redis Streams  | Локальная асинхронная обработка         |
| RabbitMQ       | Надежная маршрутизация сообщений        |
| NATS JetStream | Событийная архитектура                  |
| Kafka          | Большие потоки данных и масштабирование |

**Для первого локального прототипа я бы начал с SQLite + фоновых Python workers.** Необязательно сразу внедрять Kafka.

Важные свойства:

* повторная обработка после сбоя;
* уникальный `event_id`;
* статус обработки;
* журнал ошибок;
* повторные попытки;
* идемпотентность.

# 4. Разные источники требуют разных обработчиков

Единый Pipeline не означает, что все данные обрабатываются одинаково.

## Email

Извлекаются:

* отправитель;
* получатели;
* копии;
* тема;
* текст;
* вложения;
* время;
* цепочка переписки.

## Корпоративные чаты

Извлекаются:

* автор сообщения;
* участники;
* канал;
* ответы;
* реакции;
* ссылки на сообщения.

## Документы

Извлекаются:

* автор;
* метаданные;
* текст;
* таблицы;
* заголовки;
* версии документа.

## Телефонные разговоры

Pipeline:

```text
Audio
  │
  ▼
Speech-to-Text
  │
  ▼
Speaker Diarization
  │
  ▼
Transcript
  │
  ▼
Speaker Identity Resolution
  │
  ▼
Knowledge Extraction
```

Здесь есть отдельная сложность: **определение говорящего по голосу не равно однозначной идентификации сотрудника**. Нужны подтвержденные связи с участниками разговора и контроль ошибок.

## Ручной ввод

Например, пользователь говорит:

> «Саша из бухгалтерии отвечает за отчетность».

Система извлекает предположительный факт, но должна отличать утверждение пользователя от подтвержденных кадровых данных.

# 5. Единый Employee Identity Layer

Все источники должны обращаться к одному реестру идентичности.

```text
                  IDENTITY LAYER
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
   Outlook            Teams              CRM
       │                 │                 │
       └────────────► EMP-0042 ◄───────────┘
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
   Документы          Телефон             Чаты
```

### Пример

В Outlook:

```text
a.petrov@company.com
```

В Teams:

```text
alex.petrov
```

В CRM:

```text
User ID: 781
```

В документах:

```text
Александр Петров
```

Система связывает эти идентификаторы с:

```text
EMP-0042
```

Но каждую связь следует хранить с источником, способом установления и уровнем доверия.

# 6. Накопление знаний: Fact Store

Это один из наиболее важных компонентов.

Не нужно хранить всю информацию только как embeddings.

Я бы использовал структуру:

```text
Knowledge Store
│
├── Sources
│   └── Оригинальные данные
│
├── Facts
│   └── Извлеченные утверждения
│
├── Entities
│   └── Сотрудники / проекты / задачи
│
├── Relationships
│   └── Связи между сущностями
│
├── Events
│   └── Действия и изменения
│
└── Evidence
    └── Подтверждающие источники
```

### Пример накопления

Первое письмо:

> Александр занимается интеграцией API.

Второе письмо:

> Alex подготовил документацию API.

Третья задача:

> Ответственный за API-интеграцию — Александр Петров.

В базе постепенно формируются:

```text
EMP-0042
    │
    ├── WORKS_ON ─────► API Integration
    │
    ├── AUTHORED ─────► API Documentation
    │
    └── RESPONSIBLE_FOR ► API Integration
```

При этом каждое утверждение хранится отдельно, с источником и временным контекстом.

Нельзя считать повторение одного и того же утверждения в нескольких письмах независимым доказательством: письма могут копировать друг друга.

# 7. Гибридный поиск

Я бы не делал ставку только на Vector RAG.

Тебе нужен **Hybrid Retrieval**.

| Тип поиска       | Для чего                       |
| ---------------- | ------------------------------ |
| Exact Search     | Email, Employee ID, телефон    |
| Full-Text Search | Имена, термины, фразы          |
| Vector Search    | Семантически похожие документы |
| Structured Query | Факты, даты, должности         |
| Graph Search     | Связи между сотрудниками       |
| Temporal Search  | История изменений              |

### Пример запроса

> «Какие проекты ведет Саша из Engineering и с кем он взаимодействует?»

Pipeline:

```text
1. Identity Resolution
        │
        ▼
2. Определение сотрудника
        │
        ▼
3. Structured Query
   Проекты и должности
        │
        ▼
4. Graph Query
   Связи и взаимодействия
        │
        ▼
5. Vector Search
   Документы и обсуждения
        │
        ▼
6. Evidence Filtering
        │
        ▼
7. LLM
```

LLM получает не просто набор похожих фрагментов, а контекст из разных хранилищ.

# 8. Контур проверки и консолидации

По мере накопления данных будут появляться противоречия.

Например:

```text
Источник A:
Александр Петров — Developer

Источник B:
Александр Петров — Team Lead
```

Это может быть:

* изменение должности;
* устаревший документ;
* ошибка в источнике;
* разные сотрудники с одинаковым именем.

Система должна сохранять обе записи, а затем анализировать:

```text
Fact A
  ├── valid_from
  ├── valid_to
  ├── source
  └── status

Fact B
  ├── valid_from
  ├── valid_to
  ├── source
  └── status
```

### Knowledge Consolidation Worker

```text
Новые факты
    │
    ▼
Проверка дубликатов
    │
    ▼
Поиск противоречий
    │
    ▼
Сопоставление с существующими фактами
    │
    ▼
Обновление истории
    │
    ▼
Индексация
```

**LLM может помогать анализировать противоречия, но окончательное подтверждение важных сведений должно зависеть от политики источников и, при необходимости, человека.**

# 10. Где использовать LLM

Я бы не передавал LLM абсолютно все операции.

| Операция                   | Предпочтительный подход       |
| -------------------------- | ----------------------------- |
| Нормализация почты         | Код                           |
| Нормализация телефонов     | Код                           |
| Поиск точного ID           | База данных                   |
| Дедупликация файлов        | Хеши                          |
| Извлечение фактов          | LLM + структурированная схема |
| Идентификация по контексту | Правила + поиск + LLM         |
| Проверка противоречий      | Правила + LLM                 |
| Семантический поиск        | Embeddings                    |
| Финальный ответ            | LLM                           |

Для локальной работы можно использовать Ollama, а для более сложного извлечения — Gemini или Microsoft Foundry, если это разрешено политикой обработки данных.

# 11. Безопасность: особенно важно для корпоративных данных

При объединении всех источников появляется риск создать единый индекс, который раскрывает больше информации, чем разрешено конкретному пользователю.

Поэтому я бы заложил **Access Control до Retrieval**.

```text
User Query
    │
    ▼
Authentication
    │
    ▼
Authorization
    │
    ▼
Identity Resolution
    │
    ▼
Permission-aware Retrieval
    │
    ▼
LLM Context
```

Необходимо учитывать:

* права доступа к исходному документу;
* конфиденциальность переписки;
* персональные данные;
* ограничения на передачу информации внешним LLM;
* удаление и отзыв доступа;
* аудит запросов и ответов.

Например, наличие сотрудника в базе не означает, что любой пользователь имеет право просматривать его личный телефон, кадровые сведения или приватные сообщения.

# 12. С чего начать реализацию

Я бы разделил разработку на четыре этапа.

### Этап 1. Unified Knowledge Model

Создать:

* `Employee`;
* `Source`;
* `Document`;
* `Fact`;
* `Relationship`;
* `Event`;
* `Evidence`.

На этом этапе не требуется подключать все источники.

### Этап 2. Ingestion Framework

Создать общий интерфейс коннекторов:

```python
class BaseConnector:
    async def fetch_changes(self) -> list[dict]:
        ...

    async def normalize(self, item: dict) -> dict:
        ...
```

Конкретные коннекторы реализуют собственную работу с Outlook, Teams, файлами и другими источниками.

### Этап 3. Identity + Knowledge Processing

Добавить:

* сопоставление сотрудников;
* извлечение фактов;
* историю;
* проверку противоречий;
* сохранение доказательств.

### Этап 4. Hybrid RAG

Подключить:

* полнотекстовый поиск;
* векторный поиск;
* фильтрацию по Employee ID;
* фильтрацию по разрешениям;
* LLM-контекст.

## Моя рекомендация по архитектуре

Для твоего проекта я бы выбрал следующую стратегию:

**Не строить один огромный RAG, в который складывается всё подряд.**

Строить:

```text
Unified Enterprise Knowledge Platform
│
├── Identity Registry
├── Source Registry
├── Raw Data Store
├── Fact Store
├── Relationship Store
├── Evidence Store
├── Vector Index
└── Hybrid Retrieval API
```

RAG в этой архитектуре становится поисковым и генеративным слоем над корпоративными знаниями, а не единственным хранилищем.

### Следующий шаг

Я предлагаю спроектировать **конкретную схему базы данных и событийную модель `ai-knowledge-core`**.

В ней мы определим:

1. Таблицы сотрудников и идентификаторов.
2. Унифицированную структуру источников.
3. Схему фактов и отношений.
4. События ingestion.
5. Статусы обработки.
6. Хранение доказательств.
7. API для подключения любого источника.
8. Связь с существующим RAG в AI-Breadboard.

Это позволит сначала создать надежное ядро, а затем подключать Outlook, Teams, Gmail, документы, CRM и аудиозаписи независимо друг от друга.
